## Anthropic API Compatibility

### Request Address

```
https://api.xiaomimimo.com/anthropic/v1/messages
```

### Request Headers

The API supports the following two authentication methods. Please choose one and add it to the request headers:

**Method 1: api-key field authentication, format:**
```
api-key: $MIMO_API_KEY
Content-Type: application/json
```

**Method 2: Authorization: Bearer authentication, format:**
```
Authorization: Bearer $MIMO_API_KEY
Content-Type: application/json
```

### Request Body

#### `messages` — array (Required)

Input messages. Each input message must be an object with a role and content.

Each input message content may be either a single string or an array of content blocks, where each block has a specific type. Using a string for content is shorthand for an array of one content block of type text.

- `messages.role` — string (Required). Role of the message. Available options: `user`, `assistant`
- `messages.content` — string | array (Required). Either: (a) Text content as a single string, or (b) Array of content parts.

#### `model` — string (Required)

The model that will complete your prompt.

Available options: `mimo-v2.5-pro`, `mimo-v2.5`, `mimo-v2-pro`, `mimo-v2-omni`, `mimo-v2-flash`

#### `max_tokens` — integer

The maximum number of tokens to generate before stopping.

Note that our models may stop before reaching this maximum. This parameter only specifies the absolute maximum number of tokens to generate.

- `mimo-v2-flash`: default 65536
- `mimo-v2.5-pro`, `mimo-v2-pro`: default 131072
- `mimo-v2.5`, `mimo-v2-omni`: default 32768

Required range: `[1, 131072]`

#### `stop_sequences` — array

Custom text sequences that will cause the model to stop generating.

Our models will normally stop when they have naturally completed their turn, which will result in a response `stop_reason` of `end_turn`.

If you want the model to stop generating when it encounters custom strings of text, you can use the `stop_sequences` parameter.

#### `stream` — boolean (Default: false)

Whether to incrementally stream the response using server-sent events.

#### `system` — string | array

A system prompt is a way of providing context and instructions to model, such as specifying a particular goal or role. Either: (a) Text content as a single string, or (b) Array of content parts. The content of the system prompt.

#### `temperature` — number

Sampling temperature controls the diversity of the text generated by the model.

The higher the temperature, the more diverse the generated text will be; conversely, the lower the temperature, the more deterministic the generated text will be.

- `mimo-v2-flash`: default 0.3
- `mimo-v2.5-pro`, `mimo-v2.5`, `mimo-v2-pro`, `mimo-v2-omni`: default 1.0

Required range: `[0, 1.5]`

#### `thinking` — object

Configuration for enabling model's extended thinking.

Note: During the multi-turn tool calls process in thinking mode, the model returns a `thinking` content block alongside `tool_use` content block. To continue the conversation, it is recommended to keep all previous `thinking` content block in the messages array for each subsequent request to achieve the best performance.

- `thinking.type` — string (Required)
  - `mimo-v2-flash`: default `disabled`
  - `mimo-v2.5-pro`, `mimo-v2.5`, `mimo-v2-pro`, `mimo-v2-omni`: default `enabled`
  - Available options: `enabled`, `disabled`

#### `tool_choice` — object

How the model should use the provided tools.

- `tool_choice.type` — string (Required). `auto` means the model will automatically decide whether to use tools.
  - Note: When a value other than `auto` is passed to `type`, the backend will remove this field by default, and the model response behavior will still be equivalent to the auto mode (this logic is subject to future adjustments).
  - Available options: `auto`
- `tool_choice.disable_parallel_tool_use` — boolean (Default: false). Whether to disable parallel tool use. If set to true: When type is auto, the model will output at most one tool use.

#### `tools` — array

Definitions of tools that the model may use.

If you include tools in your API request, the model may return `tool_use` content blocks that represent the model's use of those tools. You can then run those tools using the tool input generated by the model and then optionally return results back to the model using `tool_result` content blocks.

Note: During the multi-turn tool calls process in thinking mode, the model returns a `thinking` content block alongside `tool_use` content block. To continue the conversation, it is recommended to keep all previous `thinking` content block in the messages array for each subsequent request to achieve the best performance.

Each tool definition includes:
- `name`: Name of the tool.
- `description`: Optional, but strongly-recommended description of the tool.
- `input_schema`: JSON schema for the tool input shape that the model will produce in `tool_use` output content blocks.

Tool fields:
- `tools.name` — string (Required). Name of the tool. This is how the tool will be called by the model and in `tool_use` blocks.
- `tools.description` — string. Description of what this tool does. Tool descriptions should be as detailed as possible. The more information that the model has about what the tool is and how to use it, the better it will perform. You can use natural language descriptions to reinforce important aspects of the tool input JSON schema.
- `tools.type` — string. Available options: `custom`
- `tools.input_schema` — object (Required). JSON schema for the tool input shape that the model will produce in `tool_use` output content blocks.
  - `tools.input_schema.type` — string (Required). The type of input_schema, only `object` is supported. Available options: `object`
  - `tools.input_schema.properties` — object | null. The properties of the tool input.
  - `tools.input_schema.required` — array | null. The list of properties that must be included in the tool input.

#### `top_p` — number (Default: 0.95)

Use nucleus sampling.

In nucleus sampling, we compute the cumulative distribution over all the options for each subsequent token in decreasing probability order and cut it off once it reaches a particular probability specified by `top_p`. You should either alter `temperature` or `top_p`, but not both.

Recommended for advanced use cases only. You usually only need to use temperature.

Required range: `[0.01, 1.0]`

### Non-streaming Response

- `id` — string. Unique object identifier. The format and length of IDs may change over time.
- `type` — string. For Messages, this is always `message`.
- `role` — string. Conversational role of the generated message. This will always be `assistant`.
- `content` — array. Content generated by the model.
  - **Text** — object: `content.type == "text"`, `content.text` (string) is the content of the text.
  - **Thinking** — object: `content.type == "thinking"`, `content.thinking` (string) is the reasoning content, `content.signature` (string) may be empty.
  - **Tool use** — object: `content.type == "tool_use"`, with `id`, `name`, `input` fields.
- `model` — string. The model that handled the request.
- `stop_reason` — string. The reason the message finished. Available values:
  - `end_turn`: the model reached a natural stopping point.
  - `max_tokens`: we exceeded the requested `max_tokens` or the model's maximum.
  - `tool_use`: the model invoked one or more tools.
  - `content_filter`: the content was omitted due to a flag from our content filters.
  - `repetition_truncation`: the model detects repetition.
- `usage` — object. Billing and rate-limit usage.
  - `usage.input_tokens` — integer. The number of input tokens which were used.
  - `usage.output_tokens` — integer. The number of output tokens which were used.
  - `usage.cache_read_input_tokens` — integer | null. The number of input tokens read from the cache.

### Streaming Response

- `SSE.event` — string. A string identifying the type of event described.
  - Available options: `message_start`, `content_block_start`, `content_block_delta`, `content_block_stop`, `message_delta`, `message_stop`
- `type` — string. Each server-sent event includes a named event type and associated JSON data.
- `message` — object. Response message. Contains: `message.id`, `message.type` (always `message`), `message.role` (always `assistant`), `message.model`, `message.content` (array of content blocks), `message.stop_reason`.
- `index` — integer. The position of the content block within the message.
- `content_block` — object. The content block that is starting.
  - **Text**: `content_block.type == "text"`, `content_block.text` (often empty string at start; text is appended via `content_block_delta` events of type `text_delta`).
  - **Thinking**: same shape with thinking deltas.
  - **Tool use**: same shape with input deltas.
- `delta` — object. Actual response content. Either:
  - **Content block delta**: `delta.type` is `text_delta` | `thinking_delta` | `input_json_delta`. `delta.text` is text part. `delta.thinking` is thinking part. `delta.partial_json` is a JSON fragment string (clients should concatenate fragments in arrival order to form the complete input JSON, then parse).
  - **Message delta**: incremental data for the message itself.
- `usage` — object | null. Billing and rate-limit usage (same shape as non-streaming).

## Vendor-Supplied Code Examples

### Example 1: Basic completion with thinking enabled (mimo-v2.5-pro)

```python
import os
from anthropic import Anthropic

client = Anthropic(
    api_key=os.environ.get("MIMO_API_KEY"),
    base_url="https://api.xiaomimimo.com/anthropic"
)

message = client.messages.create(
    model="mimo-v2.5-pro",
    max_tokens=1024,
    system="You are MiMo, an AI assistant developed by Xiaomi. Today is date: Tuesday, December 16, 2025. Your knowledge cutoff date is December 2024.",
    messages=[
        {
            "role": "user",
            "content": [
                {
                    "type": "text",
                    "text": "Introduce machine learning in three sentences."
                }
            ]
        }
    ],
    thinking={
        "type": "enabled"
    }
)

print(message.content)
```

### Example 4: Streaming

```python
import os
from anthropic import Anthropic

client = Anthropic(
    api_key=os.environ.get("MIMO_API_KEY"),
    base_url="https://api.xiaomimimo.com/anthropic"
)

with client.messages.stream(
        max_tokens=1024,
        system="You are MiMo, an AI assistant developed by Xiaomi. Today is date: Tuesday, December 16, 2025. Your knowledge cutoff date is December 2024.",
        messages=[
            {
                "role": "user",
                "content": "please introduce yourself"
            }
        ],
        model="mimo-v2.5-pro",
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)
```

## Notes for Future Troubleshooting

1. **No `anthropic-version` header in any vendor example.** This is why our CLI omits it. If MiMo later requires one, the symptom will be a 4xx with a missing-header error message.
2. **Vendor SDK path uses `base_url="https://api.xiaomimimo.com/anthropic"`** (no trailing `/v1/messages`). Direct HTTP calls (which our CLI makes) hit `https://api.xiaomimimo.com/anthropic/v1/messages`.
3. **Identity bias in vendor examples.** Every system prompt in vendor examples explicitly anchors MiMo's identity ("You are MiMo, an AI assistant developed by Xiaomi…"). This signals that, like DeepSeek, the model may default-claim a different identity if no anchor is provided. Our `--no-anchor` flag exists to verify that empirically.
4. **Thinking content uses `signature: ""` in vendor examples.** Unlike Anthropic's spec (which uses `signature` for verifiable thinking blocks in cache replay), MiMo returns an empty signature. Treat as informational only.
5. **`max_tokens` hard cap is `131072`** — different from Anthropic's standard cap. Sending `1_000_000` (as DeepSeek's CLI does) will likely 4xx.
6. **Image input uses `{"type": "image", "source": {"type": "url", "url": ...}}`** — URL-based, not base64. The vendor example uses an `mi-fds.com` (Xiaomi-hosted) URL; not yet verified whether arbitrary public URLs are accepted.
7. **`tool_use` returns `id` prefixed with `call_`** — not the Anthropic-standard `toolu_` prefix. Consumers parsing tool IDs by prefix should accept either.
