> **Part of [CLAUDE.md](../../CLAUDE.md)** — detail for the "Error Handling Conventions" section. Pairs with [architecture.md](architecture.md) (`kb.errors` API).

- **Exception taxonomy** (cycle 20): `kb.errors` defines `KBError(Exception)` as the base for all kb-originated errors, with 5 specialisations — `IngestError` (raised by `ingest_source`), `CompileError` (`compile_wiki`), `QueryError` (`query_wiki` / `search_pages`), `ValidationError` (input validation), `StorageError` (atomic-write / file-lock / audit-write failures; carries `kind` + optional `path` with a redacting `__str__` that emits `<path_hidden>` so log-aggregators never see raw filesystem paths). `LLMError` and `CaptureError` subclass `KBError`; `isinstance(err, Exception)` is preserved via MRO, so existing outer catches keep working. Rule: new code that needs to raise should subclass the nearest specialised `KBError` — bare `except Exception` is only acceptable at boundary layers (CLI top-level via `_error_exit`, MCP tool wrappers, `_make_api_call` retry loop, per-source continue-on-error loops inside `compile_wiki`, `ingest_source` outer AC5 wrap).
- **MCP tools**: Return `"Error: ..."` strings on failure — never raise exceptions to the MCP client. Page IDs validated via `_validate_page_id()` (rejects path traversal, verifies path within WIKI_DIR).
- **LLM calls**: Shared retry logic in `_make_api_call()` — 3 attempts with exponential backoff on rate limits/overload/timeout. `LLMError` on exhaustion. `call_llm_json()` uses forced tool_use for guaranteed structured JSON (no fence-stripping needed).
- **Page loading loops**: Catch specific exceptions (not broad `Exception`) and skip with warning — never abort a full scan for one bad file.
- **JSON stores**: All use `atomic_json_write()` (temp file + rename). Capped at 10,000 entries each (feedback, verdicts).
- **Ingest limits**: `MAX_ENTITIES_PER_INGEST=50`, `MAX_CONCEPTS_PER_INGEST=50` — prevents runaway page creation from hallucinated lists.
- **Path traversal**: Validated at MCP boundary (`_validate_page_id`, ingest path check), at library level (`refine_page`, `pair_page_with_sources`), and in reference extraction. `extract_citations()` and `extract_raw_refs()` reject `..` and leading `/`.
- **Drift pruning**: `compile.compiler.detect_source_drift` is read-only on the manifest — deletion-pruning is computed locally for the return payload but NOT persisted (cycle 4 R1 Codex MAJOR 3 made `find_changed_sources(save_hashes=False)` fully read-only). Stale deleted-source entries remain in the manifest until the next `compile_wiki` run with `save_hashes=True` writes them out; see function docstring.
- **Slug-collision hardening** (cycle 20): `_write_wiki_page(..., exclusive=True)` uses `os.open(O_WRONLY|O_CREAT|O_EXCL)` + POSIX `O_NOFOLLOW` (guarded) + write-phase poison-unlink to defeat two concurrent `ingest_source` calls from silently overwriting each other's summary. On collision raises `StorageError(kind="summary_collision", path=...)`; callers (`_run_ingest_body` summary write, `_process_item_batch` item write) pivot to `_update_existing_page` which acquires `file_lock(page_path)` unconditionally inside the helper body. `append_evidence_trail` is called OUTSIDE that lock because it acquires its own sidecar lock and `file_lock` is not re-entrant — chaining them would self-deadlock.
- **Windows directory-entry durability — WON'T-FIX, verified cycle 91** (closes the cycle-89 AC01 residual; do NOT re-derive this): on `nt` there is NO SUPPORTED unprivileged primitive that makes a directory entry durable, so `kb.utils.io._fsync_parent_dir` returns `BarrierResult.SKIPPED_PLATFORM` permanently on Windows and that is the designed end state, not a gap awaiting a fix. Verified inventory (cycle 91): (1) `FlushFileBuffers` works only on FILE handles — it rejects directory handles, and the volume-handle form (`\\.\C:`) flushes the entire volume and requires administrator privileges; (2) `NtFlushBuffersFileEx` documents `FLUSH_FLAGS_FILE_DATA_SYNC_ONLY` as "not valid with a directory handle" — even the kernel API offers no directory flush; (3) `DeleteFileW` has no write-through flag; (4) transactional NTFS (`DeleteFileTransacted`) EXISTS and is unprivileged, but is REJECTED deliberately, not overlooked: Microsoft deprecates TxF ("may not be available in future versions"; alternatives strongly recommended per its deployment guidance), and its commit guarantees under power fault are conditional — building the only Windows delete-durability path on an API its vendor says not to adopt trades a documented risk for an undocumented one. What Windows DOES give: `MoveFileExW(MOVEFILE_WRITE_THROUGH)` forces the RENAME's metadata operation to storage before returning (this is `durable_replace`'s cycle-87 Windows barrier — renames are covered), and NTFS metadata journaling (`$LogFile`) makes completed metadata ops (including deletes) crash-CONSISTENT (replayed or rolled back as a unit on mount) but not durable-on-return — a power loss immediately after `DeleteFileW` returns can resurrect the file. Consequence for callers: never describe a Windows deletion as durable; the delete-resurrection risk on Windows is ACCEPTED and deliberately UNREPORTED per-call — `capture._finish_rollback`'s indeterminacy report (`ROLLBACK_INCOMPLETE_MARKER` naming survivors) is the cross-platform mitigation, and per cycle-89's crying-wolf decision `SKIPPED_PLATFORM` is not surfaced per-call because it is constant on the platform (a note on every capture failure trains the reader to ignore it). This finding was independently re-proposed by reviewers in cycles 87, 88, and 89 — point them here. External confirmations: WASI issue #756 (no directory fsync on Windows), ayende.com "fsync()-ing a directory on Linux (and not Windows)", Microsoft `NtFlushBuffersFileEx` DDI docs, evanjones.ca durability survey.
- **Path safety** (cycle 65 AC9 + AC10, cycle 66 AC5): `src/kb/utils/path_safety.py` exports `_assert_under_project_root(path, field_name, *, require_exists=False, require_dir=False, dual_anchor=True)` for dual-anchor PROJECT_ROOT containment (literal-form on absolute paths + resolved-form always; raises `ValueError("{field}_must be inside project root")` with no path interpolation per T6 information-leak hardening). Q2.2 hard cap: 3 keyword-only parameters (cycle-66 AC5 dropped `allow_symlinks` because zero callers ever opted out; symlink rejection is now structurally unconditional). Honors `kb.config.get_project_root()` resolution order: `KB_PROJECT_ROOT` env (cycle-19 L2 reload-leak) → monkeypatched `kb.config.PROJECT_ROOT` (cycle-18 L1) → heuristic. Used by `compile/compiler.py::_validate_path_under_project_root` (which re-raises as `ValidationError` per cycle-29 contract); `mcp/app.py::_validate_wiki_dir` and `_validate_page_id` use INLINE checks instead so they can honor `_validate_wiki_dir`'s explicit `project_root=` parameter and `_validate_page_id`'s WIKI_DIR-anchored contract. AC10 adds `_open_no_follow(path)` + `_close_no_follow_fd(fd)` for TOCTOU mitigation on `rebuild_indexes` mutators (manifest, vector_db, vec_tmp): primary POSIX path uses `os.open(path, O_NOFOLLOW | O_RDONLY)` (atomic — symlink swap raises `OSError(ELOOP)`); Windows path uses `path.is_symlink()` defensive check (non-atomic but rejects existing symlinks for the local-FS threat model — a fully-atomic Windows `CreateFileW(FILE_FLAG_OPEN_REPARSE_POINT)` ctypes implementation was tried and reverted in Step 12 due to HANDLE-type correctness issues breaking real-file unlinks). Q2.3 fallback for unsupported POSIX (e.g., FUSE without O_NOFOLLOW) emits `logger.warning("AC10: O_NOFOLLOW unsupported ...")` once per process.
